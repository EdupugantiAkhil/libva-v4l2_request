# AVE encoding in the same VA driver (proposal)

Apple M-series SoCs have two separate video blocks:

* **AVD** decodes. This driver already serves it through the stateless V4L2
  Request API.
* **AVE** encodes. The `apple-ave` kernel driver exposes it as a *stateful*
  V4L2 mem2mem encoder.

Until now encoding needed a second VA driver (`ave_drv_video.so`, from
aurora-ave-vaapi) and a dispatcher driver (`j713_drv_video.so`) that loaded
both and routed each call. This change serves AVE H.264 and HEVC encoding
from `v4l2_request_drv_video.so` itself, so one `LIBVA_DRIVER_NAME` covers
decode and encode, and the dispatcher is no longer needed.

The encoder code is ported from aurora-ave-vaapi at e40b036 and keeps its MIT
licence headers:

| aurora-ave-vaapi file (`ave-vaapi/src/`) | Ported to |
|---|---|
| `v4l2_encoder.c`, `v4l2_probe.c` | `src/ave_encoder.[ch]` |
| `encode_params.c`, `surface_import.c` | `src/ave_params.[ch]` |
| `encode.c`, `capabilities.c` (VA glue), rewritten against this driver's objects | `src/encode.c` |

ave-vaapi's own decoder, objects and dispatcher are not ported; this
driver keeps its own decode path.

## Scope

* **Profiles (`VAEntrypointEncSlice`):** H.264 Constrained Baseline, Main
  and High; HEVC Main and Main 10. Main 10 needs P010 support in the UAPI
  headers.
* **Pictures:** I and P only, one slice per picture, one reference.
* **Bitstream:** Annex B with headers generated by AVE. Packed headers are
  not accepted (`VA_ENC_PACKED_HEADER_NONE`).
* **Rate control:** CBR and VBR. There is no CQP, because AVE has no
  constant-QP mode.
* **Size:** 320x240 to 4096x2304. H.264 is also limited to 36864
  macroblocks, and HEVC to 8912896 luma samples.
* **Inputs:**
  * this driver's own surfaces, written by `vaPutImage`, by
    `vaDeriveImage` + map, or by an AVD decode;
  * imported linear NV12/P010 DMA-BUFs, both legacy `DRM_PRIME` (Chrome's
    path) and `DRM_PRIME_2`.

Rate parameters that AVE cannot apply at all are refused, not ignored. Each VA field
is listed in `src/ave_params.c` as either mapped to an `apple-ave` control or
documented as having no effect. The same applies to:

* B slices;
* multiple slices;
* High tier;
* packed headers;
* temporal layers;
* ROI;
* maximum frame size.

After the first picture, AVE accepts only a new average bit rate. Changes
to the fixed frame rate, peak bit rate or QP limits are rejected at
`vaEndPicture`; unchanged repetitions are accepted. A failed submission
cancels the entire encoder session (including other outstanding frames),
because a failure may occur after OUTPUT QBUF. Destroy and recreate the
context to encode again after such a failure.

`vaRenderPicture` stores the request. The error is returned from
`vaEndPicture`, which is where FFmpeg and Chrome check for it.

## How encode fits into the driver

Encode is added as one more kind of context, next to decode and VPP. It is
not a separate driver inside the driver.

| VA object | Decode (unchanged) | Encode |
|---|---|---|
| Config | `codec` set, entrypoint VLD | `codec` NULL, entrypoint `EncSlice`. Also stores `rate_control` and `packed_headers`, and reports them through `vaQueryConfigAttributes`. |
| Context | `ctx->codec` and the request/media state | `ctx->enc` (`struct v4l2r_encode`). It owns one `apple-ave` session, which is opened at the first picture and closed by `vaDestroyContext` or `vaTerminate`. It has no decoder file descriptor and no request state. |
| Surface | Bound to one decode context (`surface->ctx`), or backed by standalone storage | **Never bound to an encode context.** `surface->encode_pending`, `encode_context` and `encode_coded` track the one encode that is reading it. `surface->import` holds an imported DMA-BUF. |
| Buffer | Parameter and slice data | Encode parameter buffers are plain memory. `VAEncCodedBufferType` gets a `struct v4l2r_coded` (segment, packet list and delivery state) in `buffer->coded`. |
| Image | Unchanged | Unchanged |

The existing handle tables (`drv->configs`, `contexts`, `surfaces`,
`buffers`) hold all of these. The ID ranges, lookups and `vaTerminate`
cleanup are the same for encode and decode objects.

### Locking

* Every encode entrypoint that changes encoder state runs under
  `drv->api_mutex`:
  * the surface API wrappers in `api.c`, already in place for
    Begin/Render/EndPicture, `vaSyncSurface`, `vaQuerySurfaceStatus`,
    `vaDestroySurfaces` and context create/destroy;
  * `vaMapBuffer` and `vaDestroyBuffer` of coded buffers, which take the lock
    themselves.
* Other buffer calls stay unlocked, as before.
* `wait_delivery()` drops `api_mutex` for 1 ms per retry while an earlier
  submission is still in flight. It revalidates the buffer, context and
  submission after reacquiring the lock.
* `drv->mutex` keeps its role of protecting the handle tables.

### One surface for both decode and encode

A surface's pixels can come from three places:

1. **Standalone backing** from the AVD CAPTURE queue: an MMAP buffer
   exported as a DMA-BUF, exactly as for any surface this driver creates.
   Uploads use `vaPutImage` or `vaDeriveImage`.
2. **A decode context's CAPTURE buffer**, when an AVD decode wrote the
   surface (the zero-copy transcode path: `-hwaccel vaapi` followed by
   `h264_vaapi`).
3. **An imported DMA-BUF** (`surface->import`), which can only be encoded.

For cases 1 and 2, encode reads the pixels through `v4l2r_surface_view()`,
the same helper `vaDeriveImage` and `vaGetImage` use:

* `v4l2r_surface_ready()` first waits for any decode still writing the
  surface;
* the view supplies pitch, plane offsets and mappings for both the
  single-plane and two-plane layouts.

For case 3, the import is mapped read-only. Each read is bracketed by
`DMA_BUF_IOCTL_SYNC` start and end, after a `POLLIN` wait for the
producer's implicit fence.

The visible rows are then copied into an `apple-ave` OUTPUT MMAP buffer
using AVE's layout: its own stride, with chroma right after `height` luma
rows. AVE cannot import DMA-BUFs into its OUTPUT queue, so this costs one
CPU copy per frame, as it did in `ave_drv_video.so`.

Encode never binds the surface or holds it after the copy.
`surface->encode_pending` only tracks whether the coded frame is done:

* `vaSyncSurface` on the input waits for the coded frame, and then for any
  decode queued into the same surface since.
* Reusing the input as another encode input, or destroying it, also waits
  for the coded frame.
* Destroying the encode context cancels the frames still in flight. Their
  coded buffers can then only be destroyed, not mapped, and every coded
  buffer of that context loses its frame; map coded buffers before
  destroying their context, as FFmpeg and Chrome do.

A surface can therefore be decoded into, encoded and read back by
`vaGetImage` in any order. The host test `ave-encode-lifetime` covers this.

Imported surfaces are refused where the driver would write them or hand out
their memory:

* decode or VPP `vaBeginPicture`;
* `vaDeriveImage`;
* `vaExportSurfaceHandle`, which returns `OPERATION_FAILED` from
  `v4l2r_surface_view`.

### Ordering and completion

`apple-ave` returns coded frames in submission order. Each frame is tagged
with its OUTPUT timestamp, `1 + (seq - 1) * 1e6 / fps` µs.

* `vaSyncSurface`, `vaQuerySurfaceStatus` and `vaSyncBuffer` (VA ≥ 1.9)
  service the queue until the frame they are waiting on is complete.
* `vaMapBuffer` of a coded buffer waits for that frame, and for any
  frame of the same context submitted earlier that is still in flight.
  Destroyed or failed submissions never hold later buffers back.
* Destroying or reusing a submitted coded buffer waits for OUTPUT as well
  as CAPTURE completion. Unready coded-buffer reuse is rejected before
  changing any state. Stale completions are ignored, and CAPTURE buffers
  are recycled. A frame larger than its coded buffer completes with
  `VA_CODED_BUF_STATUS_FRAME_SIZE_OVERFLOW`; only complete packets that
  fit are retained (there may be none).
* A forced IDR waits for the OUTPUT queue to go idle and then sets
  `V4L2_CID_MPEG_VIDEO_FORCE_KEY_FRAME`.

FFmpeg uses `vaSyncBuffer` when it is available. `ave-encode-ffmpeg`
exercises it alongside `vaSyncSurface` in both eager and async ("lazy") modes.

## Capability reporting

`vaQueryConfigProfiles` returns the decode list exactly as before. When an
encoder is present, it then appends any encode profile not already listed,
before `VAProfileNone`. So on the M4:

* the decode profiles keep their order;
* HEVC Main 10 and the H.264 profiles that are already listed for decode
  only gain an entrypoint.

| Query | Without an encoder | With `apple-ave` |
|---|---|---|
| `vaQueryConfigEntrypoints` | `VLD` when decodable (unchanged) | `VLD` when decodable, then `EncSlice` when encodable |
| `vaCreateConfig` / `vaGetConfigAttributes` | Previous logic, unchanged | Takes the encode branch only for `EncSlice` with an encodable profile; everything else falls through to the previous logic |
| `vaQuerySurfaceAttributes` on an encode config | n/a | The same 8 attributes `ave_drv_video.so` reported: pixel format, memory types, external buffer descriptor, usage hint, min/max size |
| Encode config attributes | n/a | RT format; `CBR \| VBR`; packed headers `NONE`; MaxRefFrames 1; MaxSlices 1; max picture width/height. Everything else `VA_ATTRIB_NOT_SUPPORTED`. |

Chrome sees H.264 CB/Main/High encode with min 321x241 and max 4096x2304,
exactly as with the dispatcher. `ave-encode-chrome` replays Chrome 156's
`FillSupportedProfileInfos` against these answers.

Without an encoder (no `apple-ave` node, or `LIBVA_V4L2_ENCODE=0`), the
driver behaves as before:

* encode buffer types are still `UNSUPPORTED_BUFFERTYPE`;
* `EncSlice` configs are still `UNSUPPORTED_ENTRYPOINT`;
* `DRM_PRIME` import descriptors are ignored as before. Decode never
  imported, so honouring them would only make allocation fail differently.

`ave-encode-capabilities` and `ave-encode-decode-isolation` check this.

## Device discovery

The encoder is probed once, in `__vaDriverInit`, after decoder enumeration
succeeds:

1. List `/sys/class/video4linux/video*` (indices up to 64) and keep nodes
   whose `name` is exactly `apple-ave`. Node numbers are never assumed;
   current kernels register AVE at `video10` (`apple-video-nr.h`).
2. Open each match, check `VIDIOC_QUERYCAP` (M2M multiplanar, streaming),
   enumerate formats (H.264/HEVC CAPTURE, NV12/P010 OUTPUT), and close it.
3. Record the first match in `drv->ave`.

The probe holds no file descriptor. Each encode context opens its own
session at its first picture, so decode-only processes never keep the
encoder open, and several encode contexts can coexist up to the kernel's
session limit.

Environment variables:

* `LIBVA_V4L2_ENCODE=0` or `off` disables encode at run time.
* `LIBVA_V4L2_ENCODE_DEVICE=/dev/videoN` selects a node. It must still
  carry the `apple-ave` sysfs name.

The driver still needs a decoder to initialise, because surface backing
comes from the AVD CAPTURE queue. A system with AVE but no AVD is out of
scope here; see the open questions below.

## Build options

* `-Dave_encode=auto|enabled|disabled` (feature, default `auto`).
  * `auto` builds encode when the headers provide the VA encode structures,
    the DRM PRIME descriptor, `DMA_BUF_IOCTL_SYNC` and the stateful V4L2
    HEVC controls.
  * `enabled` fails configuration if they are missing.
  * `disabled` builds exactly the previous driver; `src/encode.c` and the
    ported files are not compiled.
* The configure summary prints an `ave encode:` line next to the codec
  lines.
* Main 10 also needs `HAVE_V4L2_PIX_FMT_P010` (Linux 6.0 UAPI).
* `vaSyncBuffer` is wired up only with VA ≥ 1.9 (libva 2.9). Older libva
  falls back to `vaSyncSurface`, which FFmpeg also handles.

## Removing the dispatcher

With this change, `LIBVA_DRIVER_NAME=v4l2_request` (or the distribution's
alias for this driver) serves decode and encode. `j713_drv_video.so` and
`ave_drv_video.so` can then be dropped. The packaging change belongs in the
distribution (nixos-aurora) and is not part of this repository.

Without the dispatcher:

* FFmpeg's `-vf format=nv12,hwupload -c:v h264_vaapi` works, because its
  unhinted upload surfaces are ordinary surfaces of the same driver. The
  dispatcher sent them to the decoder, which could not encode them.
* Chrome's WebCodecs encode imports frames into the same driver that
  advertised the encode profiles.

## Tests

`tests/ave-encode.c` runs as nine meson tests (`ave-encode-*`). They use a
model AVD that only provides CAPTURE storage as real memfds, so CPU writes
and encode reads share memory, and a model `apple-ave` that follows
`ave-v4l2.c`.

| Test | Covers |
|---|---|
| `units` | Ported from `test_ave_units.c`: control values against the `apple-ave` control table, VA rate mapping, AVE frame packing, import layouts, sysfs probe filter |
| `capabilities` | Decode answers with and without an encoder; encode attributes |
| `decode-isolation` | No imports and no encode buffers without an encoder |
| `chrome` | Ported from `test_chrome_gating.c`: Chrome profile gating, packed-header/B-slice/multi-slice/High-tier refusal, read-only imports, FFmpeg Main 10 sequence |
| `ffmpeg` | Ported from `test_fake_ave.c`: H.264, HEVC and Main 10 at 720p and 1080p (coded 1088), eager and async, AVE layout, visible-row endpoints and representative packed rows checked |
| `import` | Chrome-shaped `DRM_PRIME` import encode with `DMA_BUF_SYNC` bracketing |
| `lifetime` | `vaPutImage`, encode and `vaGetImage` on one surface; teardown orders with encodes in flight |
| `completion` | Destroy unmapped output and keep encoding; coded-buffer reuse and overflow |
| `faults` | CAPTURE-before-OUTPUT completion, in-flight coded reuse, immutable rate changes, post-QBUF STREAMON failure. `import` also injects DMA-BUF END-sync failure |

## Open questions for maintainers

1. **AVE-only systems.** Initialisation still needs a decoder, because
   standalone surfaces are backed by the decoder's CAPTURE queue. Should
   encode-only operation be supported, with heap or udmabuf backing when
   there is no decoder, or is AVD always present on the hardware this driver
   targets?
2. **Device-specific code.** The encoder backend is tied to `apple-ave`: the
   sysfs name match, the control table and the payload layout. Should it
   stay that way, or be generalised now to other stateful V4L2 encoders?
   Venus is where the code originally came from.
3. **Vendor string.** `str_vendor` is unchanged. Some clients (Chrome's
   `VAImplementation`) classify drivers by vendor string; encode does not
   need a change there, but the maintainers may want one.
4. **The copy into AVE.** Each frame is copied by the CPU into AVE's OUTPUT
   buffer. Removing the copy needs DMABUF import on `apple-ave`'s OUTPUT
   queue, which is a kernel change and out of scope here.
